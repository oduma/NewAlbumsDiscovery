## Phase 1: Cross-Platform Application Scaffolding — ✅ COMPLETE (2026-08-12)

### Goal
Stand up the empty solution/project skeleton for New Albums Discovery as a .NET 10 cross-platform background worker (Windows Service / Linux daemon), with the layered architecture, DI wiring, configuration, and logging plumbing in place — but **no feature logic** (no MusicAggregator/AIDiscovery/Notification business code, no SQLite/Gemini/Telegram integrations). Those land in later phases.

### Decisions (confirmed with user 2026-08-12)
1. **Project granularity:** One project per architectural layer (Domain, Application, Infrastructure, Worker). The three bounded contexts (`MusicAggregator`, `AIDiscovery`, `Notification`) exist as namespace folders inside each layer, not as separate projects. Context isolation is enforced by convention/code review, per `docs/constitution/DDD-architecture.md` §4 red flags.
2. **Test framework:** xUnit, with Moq for mocking (per `docs/constitution/tdd.md` §3 example tooling).
3. **Phase 1 scope:** Pure skeleton only — solution + empty layered projects (with namespace folders per context), DI container wiring, `IOptions<T>` configuration binding pattern, logging, and cross-platform hosting (`.UseWindowsService()` / `.UseSystemd()`). Test projects are created and wired to the solution but contain no test files yet (no feature code exists to test). No SQLite/Gemini/Telegram code.
4. **CI:** Deferred. Phase 1 only needs to build and run locally via `dotnet build` / `dotnet run`.

### As-Built Corrections (discovered during implementation)
The following deviate from the original plan and supersede it — this section is the authoritative record of what actually shipped:
- **No `AddDomainServices()` extension.** `Domain` does not get a DI registration method. Adding one would require a `Microsoft.Extensions.DependencyInjection` package reference in `Domain`, which violates the Zero-Dependency Rule (`docs/constitution/DDD-architecture.md` §1). Only `Application` (`AddApplicationServices()`) and `Infrastructure` (`AddInfrastructureServices()`) participate in DI wiring; `Domain` stays out of that chain entirely until it has something to register.
- **Hosting API:** `Program.cs` uses `Host.CreateDefaultBuilder(args)` (returns `IHostBuilder`), not `Host.CreateApplicationBuilder(args)` (returns `HostApplicationBuilder`). The latter has no `.UseWindowsService()`/`.UseSystemd()` surface in this SDK — those extensions require `IHostBuilder`.
- **Logging:** settled on the built-in `Microsoft.Extensions.Logging` console provider (no Serilog), keeping Phase 1's footprint minimal.
- **Solution file format:** `dotnet new sln` on the installed .NET 10 SDK (10.0.204) generates `NewAlbumsDiscovery.slnx` (the new XML solution format), not the classic `.sln`. Kept as-is — `dotnet sln add`/`dotnet build`/`dotnet test` all work against it transparently.
- **`global.json` added** at repo root, pinning the SDK to `10.0.204` (`rollForward: latestFeature`) — not in the original plan, but needed because multiple SDKs (9.0.205, 9.0.304, 10.0.204) are installed and the build must deterministically target .NET 10.

## Phase 2: Environment Variable Developer Setup Scripts — ✅ COMPLETE (2026-08-12)

**Source:** `docs/requirements/phase2-requirements.md` (Antigravity-owned input spec — see `.agents/rules/multi-agent-governance.md`), finalized here after clarification.

### Goal
Cross-platform developer setup scripts (`scripts/setup-env.ps1` for Windows, `scripts/setup-env.sh` for Linux) that scan `z-com-ai/*.txt`, resolve each file's content as a path relative to the current user's home directory, and persist the result as a Machine-level `NewAlbumsDiscovery__*` environment variable — so a Windows Service or Linux daemon running under a system account can read it. `z-com-ai/` is already `.gitignore`'d (`*z-com-ai` in `.gitignore`) and currently contains one input file, `sqlite-db-path.txt` (content: `DB`).

### Decisions (confirmed with user 2026-08-12)
1. **Filename → env var mapping: pure mechanical transform.** No manifest file, no lookup table. Algorithm: strip `.txt` → split remaining filename on `-` → PascalCase each segment (uppercase first character, lowercase the rest) → join with `__` → prefix `NewAlbumsDiscovery__`.
   - Example: `sqlite-db-path.txt` → `NewAlbumsDiscovery__Sqlite__Db__Path`.
   - **This deviates from the literal example in `phase2-requirements.md` §2** (`NewAlbumsDiscovery__Database__Path`), which was not a mechanical transform of the filename and could only be reproduced via a manifest/lookup table. The user explicitly chose the mechanical-transform approach (true zero-touch extensibility — §5) over reproducing that exact example, so this section is the authoritative name for `sqlite-db-path.txt` going forward. `docs/specs/technical-specs.md` should be treated as needing a matching update in a later docs pass if it references `Database__Path` directly.
2. **Linux persistence target: `/etc/environment` + a systemd scaffold file.** The script upserts each variable into `/etc/environment` (read by PAM at login) **and** into `/etc/newalbumsdiscovery.env` (plain `KEY=value`, no quotes — forward-compatible with a future systemd unit's `EnvironmentFile=/etc/newalbumsdiscovery.env` directive). **Known gap, explicitly out of scope for this phase:** systemd-managed services do not inherit `/etc/environment` — wiring the actual daemon's unit file to read `/etc/newalbumsdiscovery.env` is deferred to the future deployment phase that creates the systemd unit.
3. **Session refresh: yes, best-effort.** After the Machine-level write, both scripts also apply the same values to their own process environment for immediate feedback/verification. Documented platform asymmetry (see Design Notes) rather than silently promising something that doesn't fully work:
   - **Windows:** running `.\scripts\setup-env.ps1` directly (not dot-sourced) executes in the *same* PowerShell process/session, and `$env:` writes are process-scoped — so the calling terminal sees the variable immediately with no special invocation needed.
   - **Linux:** running `./scripts/setup-env.sh` executes in a **child process**; `export` there is invisible to the parent shell unless the script is `source`d (`source scripts/setup-env.sh`). The script detects whether it was sourced and prints a warning with the correct invocation if not.
4. **No directory creation.** The script only resolves the path and persists the env var. Provisioning the actual folder (e.g. creating `%USERPROFILE%\DB`) is left to the application or the developer — out of scope here.

### As-Built Corrections (discovered during implementation and testing)
- **Real bug found and fixed in `setup-env.sh`: `return` inside a nested function cannot abort a sourced script.** The original design had a `fail()` helper that did `return 1` when `$SOURCED=1`. That `return` only unwinds `fail()`'s own call frame — it does **not** stop the sourced script itself, so a non-root + sourced run would print the error and then keep executing into privileged operations instead of stopping cleanly. Proven with an isolated repro (`source`d probe script continued past the "abort" point and printed an unreachable line) before being fixed. **Fix:** every abort/early-return point is now inlined directly at the script's own top level (not inside any helper function) — the `SOURCED`-conditional `return`/`exit` choice is repeated at each of the four exit points (root check, empty-directory, no-`.txt`-files, and the natural end) rather than centralized, because only a top-level `return` correctly unwinds a sourced script.
- **Second finding, fixed alongside the first: sourcing leaked `set -euo pipefail` into the caller's shell.** Since `source` merges the sourced script's shell-option changes into the caller, a developer following the documented `source scripts/setup-env.sh` advice would have `errexit`/`nounset`/`pipefail` silently turned on in their own interactive shell afterward — a real surprise for anyone not expecting it. **Fix:** the script now snapshots the caller's shell options (`set +o`) before applying its own `set -euo pipefail`, and restores them via a `restore_shell_opts` helper at every exit point (this one *is* safely centralized in a function, since restoring global shell-option state doesn't have the same top-level-only constraint that aborting a sourced script does).
- **Runtime-verified via WSL (Ubuntu), not just reviewed.** The original plan flagged the Linux script as "cannot be runtime-verified" in this Windows environment. WSL turned out to be available, so `setup-env.sh` was actually executed (as both a non-root and root user) rather than only reviewed: non-root+executed (blocked, exit 1, no writes), root+executed-not-sourced (persisted correctly, correct "not sourced" warning printed), root+sourced (persisted **and** immediately visible in that same shell via `$NewAlbumsDiscovery__Sqlite__Db__Path`), idempotent rerun (line count stayed at 1 in both `/etc/environment` and `/etc/newalbumsdiscovery.env`, no duplicates), and dynamic pickup of a second, temporary `.txt` file with zero script changes. All temporary test files/variables (Windows Machine scope and the WSL instance's `/etc/environment`/`/etc/newalbumsdiscovery.env`) were cleaned up afterward, except the real `NewAlbumsDiscovery__Sqlite__Db__Path` Machine value on this Windows machine, which the user chose to keep since it reflects real `z-com-ai/sqlite-db-path.txt` content.
- **`setup-env.ps1`'s elevated path required a live UAC prompt to verify**, which an automated tool cannot click through. The user approved a `Start-Process -Verb RunAs` prompt in the moment to allow real verification (elevated set, non-elevated block, dynamic file pickup, safe rerun) rather than settling for code review only.

### Design Notes (Solution-Architect-level implementation calls, not re-litigated with the user)
- **Elevation is a hard gate, not a soft warning.** Both scripts check privilege *before* touching any file/registry state:
  - Windows: `([Security.Principal.WindowsPrincipal][Security.Principal.WindowsIdentity]::GetCurrent()).IsInRole([Security.Principal.WindowsBuiltInRole]::Administrator)`. If false, print instructions to re-run from an elevated PowerShell window and `exit 1` — no partial writes.
  - Linux: `[ "$(id -u)" -eq 0 ]`. If false, print instructions to re-run with `sudo` and `exit 1` — no partial writes.
- **Idempotent upsert, not blind append.** Rerunning either script (e.g. after editing a `.txt` file's content) must update the existing line for a given key rather than duplicating it — applies to `[Environment]::SetEnvironmentVariable` (naturally idempotent) and to both Linux env files (find-existing-key-and-replace, else append).
- **Path resolution uses proper path-combine APIs** (`Join-Path` / equivalent), not naive string concatenation, so trailing slashes or separator style in the `.txt` content don't break the result.
- **`z-com-ai/` location is resolved relative to the script's own location** (`$PSScriptRoot\..\z-com-ai` / `$(dirname "$(readlink -f "${BASH_SOURCE[0]}")")/../z-com-ai`), not the caller's current working directory, so the scripts work regardless of where they're invoked from.
- **Assumption:** resolved paths do not contain the `|` character (used as the sed delimiter for the Linux upsert) or literal newlines. Spaces are fine. Not defended against exotic inputs — acceptable for this narrow scope.

### In Scope
- `scripts/setup-env.ps1` — Windows setup script per the above.
- `scripts/setup-env.sh` — Linux setup script per the above.
- Elevation/privilege checks in both, gating all writes.
- Dynamic enumeration of `z-com-ai/*.txt` (adding a new `.txt` file requires zero script changes, per §5 of the source spec).

### Out of Scope (future phases)
- Any systemd unit file / service installation (the `/etc/newalbumsdiscovery.env` scaffold is prepared for it, not consumed by it yet).
- Any change to `docs/specs/technical-specs.md`'s example env var names.
- Uninstall/rollback script (removing previously-set machine variables).
- Validating or creating the resolved directory.
- CI or automated testing of the scripts (they require elevated/root execution and machine-level state mutation, which isn't practical to sandbox in this phase).

## Phase 2.1: Environment Variable Rename — Read-Only Database Path — 📋 PLANNED (2026-08-12)

**Source:** Architecture update in `docs/requirements/high-level-requirements.md` and `docs/specs/technical-specs.md` (dual-database architecture), which renamed the read-only database's env var from the Phase 2-era `NewAlbumsDiscovery__Sqlite__Db__Path` to `NewAlbumsDiscovery__Database__LovedTracksDbPath`. Finalized here after clarification.

### Goal
Update the Phase 2 developer setup scripts (`scripts/setup-env.ps1`, `scripts/setup-env.sh`) so the read-only loved-tracks database path is published under its new name, `NewAlbumsDiscovery__Database__LovedTracksDbPath`, with a value that resolves to the full database file path (not just a folder) — matching the dual-database architecture now specified in `docs/specs/technical-specs.md` §3. Also clean up the now-obsolete `NewAlbumsDiscovery__Sqlite__Db__Path` Machine-level variable created by the original Phase 2 testing.

### Decisions (confirmed with user 2026-08-12)
1. **Mechanical-transform algorithm extended, not abandoned.** Hyphen (`-`) keeps its Phase 2 meaning: it starts a new `__`-joined top-level segment. New rule added: an underscore (`_`) within a segment marks a *compound word* — each `_`-separated sub-word is PascalCased and concatenated with **no** separator between them (separators only go between top-level hyphen segments). Example: `database-loved_tracks_db_path.txt` → `Database` + `__` + `LovedTracksDbPath` → `NewAlbumsDiscovery__Database__LovedTracksDbPath`. Filenames with no underscores behave exactly as before Phase 2.1 — fully backward compatible.
2. **File content now includes the database filename, not just the folder.** Per `docs/specs/technical-specs.md` §2.A (`.../DB/loved-tracks.db`), the source `.txt` file's content changes from `DB` to `DB/loved-tracks.db` — a full path relative to the user's home directory. **Convention: file content always uses forward slashes (`/`) as the separator, regardless of target OS** — both `Join-Path` (PowerShell) and the existing string-concatenation join (Bash) handle `/` correctly; a literal backslash would silently produce a garbage path on Linux.
3. **`z-com-ai/loved-tracks-db-path.txt` (already renamed and content-updated by the user ahead of this plan) will be renamed again, to `z-com-ai/database-loved_tracks_db_path.txt`.** The current on-disk filename is hyphen-only (no `database` segment, no underscore) and does not encode the new compound-word convention — mechanically it would still produce `NewAlbumsDiscovery__Loved__Tracks__Db__Path`, not the approved target `NewAlbumsDiscovery__Database__LovedTracksDbPath`. Content (`DB/loved-tracks.db`) is already correct and stays unchanged.
4. **Old variable is actively cleaned up, not just left stale.** Both scripts gain a small hardcoded "deprecated variable names" list (currently just `NewAlbumsDiscovery__Sqlite__Db__Path`) and remove each one every time the script runs — Machine scope + current session on Windows; `/etc/environment` + `/etc/newalbumsdiscovery.env` lines + current-session `unset` (if sourced) on Linux. Idempotent: running against an already-cleaned machine is a silent no-op for that variable.

### Design Notes
- No change to the elevation/root gating, idempotent-upsert-for-new-variables logic, or sourced-shell handling from Phase 2 — reused as-is.
- The second new variable implied by the updated architecture, `NewAlbumsDiscovery__Database__AppDbPath` (the app's own read-write database, under `<AppBaseDirectory>/Database/`, not the user's home directory), is **out of scope** here — it isn't a home-relative path sourced from a `z-com-ai/*.txt` file the way `LovedTracksDbPath` is, so it doesn't fit this scripts' model. It will be addressed separately.
- `docs/requirements/phase2-requirements.md` remains untouched (Antigravity-owned source spec, per `.agents/rules/multi-agent-governance.md`) — only this file reflects the update.

### In Scope
- Rename `z-com-ai/loved-tracks-db-path.txt` → `z-com-ai/database-loved_tracks_db_path.txt` (content unchanged: `DB/loved-tracks.db`).
- Extend `ConvertTo-EnvVarName` (`setup-env.ps1`) and `to_env_var_name` (`setup-env.sh`) with the underscore-compound-word rule.
- Add deprecated-variable cleanup (`NewAlbumsDiscovery__Sqlite__Db__Path`) to both scripts.
- Update both scripts' header-comment documentation of the naming algorithm.

### Out of Scope
- `NewAlbumsDiscovery__Database__AppDbPath` and any other new variables implied by the updated architecture (Gemini, Telegram, etc.) — not part of this narrow rename task.
- Any application code that actually opens/reads either database (Phase 3+ concern).
- Updating `docs/requirements/phase2-requirements.md`.

### Acceptance Criteria
- Given `z-com-ai/database-loved_tracks_db_path.txt` (content `DB/loved-tracks.db`), running the elevated/root script sets `NewAlbumsDiscovery__Database__LovedTracksDbPath` = `<home>/DB/loved-tracks.db`.
- A filename with no underscores (e.g. a synthetic `gemini-api-key.txt`) still produces the old-style flat name (`NewAlbumsDiscovery__Gemini__Api__Key`) — regression check confirming the extension doesn't break Phase 2 behavior.
- The stale `NewAlbumsDiscovery__Sqlite__Db__Path` variable is removed (Windows: Machine scope + current session; Linux: `/etc/environment`, `/etc/newalbumsdiscovery.env`, current session if sourced) after running either script.

## Phase 3: Music Preference Aggregator Engine & Storage — ✅ COMPLETE (2026-08-12)

**Source:** `docs/requirements/phase3-requirements.md` (Antigravity-owned input spec — see `.agents/rules/multi-agent-governance.md`), finalized here after clarification. This is the first phase to add real feature code on top of the Phase 1 skeleton — no EF Core, `DbContext`, or repository yet exists in the solution.

### Goal
Implement Feature 1 (Music Preference Aggregator): read all `LovedTracks` from the external read-only `loved-tracks.db`, run a pure, deterministic 3-level cascading-threshold aggregation in memory, and atomically replace the `AggregatedBuckets` table in the internal `new-albums-discovery.db` — end-to-end and observable (the Worker actually runs it), not just scaffolded.

### Decisions (confirmed with user 2026-08-12)
1. **Domain purity for Id/timestamp generation:** `BucketAggregatorEngine.Aggregate(...)` takes `DateTime asOfUtc` as an explicit parameter (supplied by the caller) rather than reading a wall clock internally. Each `AggregatedBucket` generates its own `Guid` Id internally via `Guid.NewGuid()` — this doesn't hurt determinism because tests assert on `BucketName`/`BucketType`/`Country`/`Language`/`Genre`/`TrackCount`, never on the Id. `asOfUtc` is sourced by the Application-layer command handler from an injected `TimeProvider` (`TimeProvider.System` in production, `FakeTimeProvider`/stub in tests) — never `DateTime.UtcNow` called directly inside Domain or Application code.
2. **Malformed/missing source data — fallback, never skip or throw.** Null/empty `CountryOrRegion` is normalized to the literal value `"Unknown"`. Null or invalid-JSON `LanguagesJson`/`GenresJson` is normalized to an empty list (contributes zero to language/genre counts for that track). **This normalization happens at the Infrastructure boundary** (`LovedTrackRepository`, mapping raw external rows into the Domain-layer `LovedTrackPreferences` value object) — the value object's constructor then enforces "Country is never null/empty, Languages/Genres are never null" as a Domain invariant, so `BucketAggregatorEngine` itself never needs a null/malformed-data branch. This keeps the engine's 100%-branch-coverage surface limited to genuine aggregation logic, per `docs/constitution/tdd.md` §3 (infrastructure isolation) — the messy boundary is isolated in Infrastructure, tested there.
3. **EF Core migrations: full, applied at startup.** Phase 3 runs `dotnet ef migrations add InitialCreate` for `AppDbContext` (committed to the repo) and calls `Database.Migrate()` once during Worker startup (in `Program.cs`, before `host.Run()`), so `new-albums-discovery.db` and its `AggregatedBuckets` table are created automatically on first run. `LovedTrackDbContext` (the external, read-only database) gets **no** migrations — this app never changes its schema.
4. **Worker wiring: runs once at startup.** A new `AggregationStartupWorker : BackgroundService` sends `AggregateMusicPreferencesCommand` via MediatR once when the Worker starts, on a background thread (`Task.Run`, honoring the host's `CancellationToken` per `phase3-requirements.md` §2), so the full pipeline is observable end-to-end on every run. The existing `HeartbeatWorker` is untouched and keeps running alongside it. Real periodic/monthly scheduling is deferred to a later orchestration phase.

### Design Notes (Solution-Architect-level implementation calls, not re-litigated with the user)
- **Grouping key at Level 2/3 is composite, not global.** Level 2 groups by `(Country, Language)` — not by `Language` alone across all cascading countries — and Level 3 by `(Country, Language, Genre)`. This is implied by the DDL (every bucket has exactly one non-null `Country`) and the worked examples (`"Netherlands/Swahili"` keeps `Country = "Netherlands"`); grouping by `Language` alone would merge tracks from different cascading countries into one bucket with an ambiguous `Country`, which the schema doesn't allow.
- **Threshold values cross the Domain/Application boundary as a Domain value object, not `AggregatorSettings` directly.** `AggregatorSettings` (the `IOptions<T>`-bound class) lives in Application per `phase3-requirements.md` §5 and must not be referenced by Domain (Domain depends on nothing, including Application — the dependency only flows the other way). A new Domain-layer `AggregationThresholds` value object (`CountryRegionThreshold`, `CountryRegionLanguageThreshold`, `MinimumBucketThreshold`) is the actual engine parameter; the command handler maps `AggregatorSettings` → `AggregationThresholds` before calling the engine.
- **`LovedTrackDbContext` maps `LovedTracks` as a keyless entity type (`HasNoKey()`).** The real external schema's primary key column/type is unknown (no sample database or column list beyond `CountryOrRegion`/`LanguagesJson`/`GenresJson` exists in this repo). Since access is strictly read-only and we only ever project the three known columns, treating it as a keyless read-only view avoids guessing a PK that could be wrong. **Flagged for correction** if the real schema turns out to require identity tracking.
- **`NewAlbumsDiscovery__Database__AppDbPath` gets a code-level default, no setup-script entry.** Unlike `LovedTracksDbPath` (which varies per developer's home directory and is why Phase 2/2.1 scripts exist), the app DB path is always `<AppBaseDirectory>/Database/new-albums-discovery.db` — mechanically derivable at runtime via `AppContext.BaseDirectory`. Infrastructure DI registration uses the env var/config value if present (for override flexibility, matching `technical-specs.md` §3's documented key), otherwise falls back to the computed default. The app itself creates the `Database` subfolder if missing (nothing else provisions it); the external `loved-tracks.db` path is never created by this app if missing — that's a hard failure (it's owned by another product).
- **EF Core maps directly to the Domain `AggregatedBucket` entity** (private setters + an EF-only constructor, `BucketType` enum stored as its string name via `HasConversion<string>()`) rather than introducing a separate Infrastructure-only persistence model — the entity is simple enough that a 1:1 mapping doesn't strain `coding-principles.md` §3's "no complex mapping" KISS guidance. `Infrastructure` referencing `Domain` types is expected/required (only `Domain` itself must stay dependency-free).
- **Infrastructure repository tests hit real SQLite** (temp file per test, not mocked) — this is the isolation boundary itself, per `tdd.md` §3; mocking is for the layers that *consume* the repository interfaces (Application), not for testing the repository implementation.

### Decisions (confirmed with user 2026-08-12)

Every other `.txt` file's trimmed content is now persisted **verbatim** as the env var value — no `Join-Path`/home-directory concatenation. The existing mechanical filename→var-name transform (hyphen = new `__` segment, underscore = compound word within a segment) is unchanged; only the *value* handling gains the branch. Both scripts' header comments get updated to document the two branches.
3. **Orchestration: `DiscoverAlbumsCommand` is a standalone MediatR command, decoupled from `AggregateMusicPreferencesCommandHandler`.** It is not called inline from Phase 3's handler and not wired into any hosted service or `Program.cs` startup sequence in this phase — **the user explicitly deferred that wiring to a future phase.** It reads whatever `AggregatedBuckets` currently exist via `IAggregatedBucketRepository` at the moment it's invoked (manually, via a test, or by whatever future orchestration phase adds), so the discovery pipeline is fully correct and independently runnable/testable even though nothing yet triggers it automatically.
4. **Dedup rule: global, case-insensitive `(Artist, Album)` match.** An album already present anywhere in `DiscoveredAlbums` — regardless of which bucket originally found it — is never inserted again. ### Design Notes (Solution-Architect-level implementation calls, not re-litigated with the user)
- **`GeminiOptions` vs. the raw API key follow Phase 3's existing split, not a new pattern.** Tunable, non-secret settings (`Model`, `MaxAlbumsPerPrompt`, `Timeframe`, `MaxRetryAttempts`, `InitialBackoffSeconds`) bind via `IOptions<GeminiOptions>` from `NewAlbumsDiscovery:Gemini` in `AddApplicationServices` — exactly like `AggregatorSettings`. The API key itself is read directly via `configuration["NewAlbumsDiscovery:GeminiApiKey"]` inside `AddInfrastructureServices` and fails fast with a descriptive `InvalidOperationException` if missing — exactly like `LovedTracksDbPath`/`AppDbPath` — rather than being folded into the bound options object, since it lives at a different, flatter config path than the `Gemini:` section.
- **Prompt templates are copied, not moved, into the Infrastructure project as embedded resources** (`src/NewAlbumsDiscovery.Infrastructure/Gemini/Prompts/*.md`, `<EmbeddedResource>`), loaded once via reflection and populated by simple `{{placeholder}}` substitution. `docs/specs/assets/prompts/*.md` stays untouched as the canonical spec copy — the app must not depend on the `docs/` folder existing at deployment time.
- **Template selection is driven by which of `AggregatedBucket.Language`/`.Genre` are non-null**, not by `BucketType` — `Genre != null` → `country-language-genres-prompt.md` (see drift note above — plural filename/placeholder, populated with the bucket's single genre); else `Language != null` → `country-language-prompt.md`; else → `country-prompt.md`. This avoids AIDiscovery's Application/Infrastructure layers needing to reference `MusicAggregator`'s `BucketType` enum at all; only the already-shared `AggregatedBucket` shape (via `IAggregatedBucketRepository`, newly extended with `GetAllAsync`) crosses the bounded-context boundary, and only at the Application-orchestration level — never Domain-to-Domain, per `docs/constitution/DDD-architecture.md` §4's guardrail.
- **`GeminiClient` is split into a thin `IGeminiApiClient` (raw SDK call: prompt string in, raw response text out) and `GeminiDiscoveryClient : IGeminiDiscoveryClient`** (template rendering, JSON parsing, the retry/backoff loop, template selection). `IGeminiApiClient`/its `Mscc.GenerativeAI`-wrapping implementation is the genuine untestable edge and is exempted from the branch-coverage mandate, exactly like `AppDbContext`/`LovedTrackDbContext` were in Phase 3. `GeminiDiscoveryClient`'s control flow, however, is ordinary orchestration logic over a mockable dependency (`IGeminiApiClient`) and **is** held to normal coverage expectations via `Moq` — same treatment as an Application command handler, just physically located in Infrastructure because `IGeminiDiscoveryClient` (the Application-facing port) is the abstraction `tdd.md` §3 requires.
- **Dedup logic lives in Domain as a pure static service**, `AlbumDeduplicator.SelectNew(candidates, existingKeys)`, operating over a new immutable `AlbumKey` value object (case-insensitive, trimmed `(Artist, Album)` normalization) — mirroring `BucketAggregatorEngine`'s pure-engine-plus-application-orchestration split from Phase 3, and giving the dedup rule itself a 100%-branch-coverage, mock-free test surface.
- **`DiscoveredAlbums` is a new `DbSet` on the existing `AppDbContext`**, added via a second EF Core migration (`AddDiscoveredAlbums`) — not a new `DbContext`. This is the migration Phase 3's Out-of-Scope section flagged as deferred here. Every constructor-bound property gets its own explicit `entity.Property(...)` call in `OnModelCreating`, learned the hard way in Phase 3's As-Built Corrections.
- **`IAggregatedBucketRepository` gains a `GetAllAsync(CancellationToken)` method** (it previously only exposed `ReplaceAllAsync`) — the read side `DiscoverAlbumsCommandHandler` needs to enumerate the current buckets.
- **`IDiscoveredAlbumRepository.AddRangeAsync` is additive, not a replace.** Unlike `AggregatedBucketRepository.ReplaceAllAsync`'s delete+insert, discovered albums accumulate over time — a new run must never wipe previously discovered albums, only add newly-found, non-duplicate ones.
- **Malformed-JSON handling degrades per-bucket, not globally.** If a bucket's prompt exhausts all retry attempts (rate-limited or malformed JSON), `GeminiDiscoveryClient` logs the failure (`ILogger<GeminiDiscoveryClient>`) and returns an empty candidate list for that bucket rather than throwing — one bad bucket must not abort discovery for every other bucket in the same run.
- **`Mscc.GenerativeAI`'s NuGet version is pinned in `Directory.Packages.props` at implementation time** (via `dotnet add package Mscc.GenerativeAI`, then moving the resolved version into central package management, matching how every other dependency in this repo is pinned) rather than guessed here.

## Phase 5: AIDiscovery Scaffolding & Bucket Processing Pipeline — ✅ COMPLETE (2026-08-13)

**Source:** `docs/requirements/phase5-requirements.md` (Antigravity-owned input spec — see `.agents/rules/multi-agent-governance.md`), finalized here after clarification.

### Goal
Bridge Phase 3's aggregation output to Phase 4's (still-unwired) Gemini engine by building the **automatic orchestration and pipeline scaffolding** the requirements call for — without yet making real Gemini calls. Concretely: 30 seconds after `AggregateMusicPreferencesCommand` finishes successfully, an `AIDiscovery` pipeline runs automatically, made of three isolated stages (start notice → per-bucket processing loop, paced 10 seconds apart, buckets visited in descending `TrackCount` order → completion report), each stage's current behavior being nothing more than printing to a dedicated notification abstraction. Also relocates the two remaining prompt templates and the country→language lookup file from `docs/specs/assets/` into `src/`, as pure (currently unconsumed) asset copies.

### Decisions (confirmed with user 2026-08-13)
1. **Orchestration: a new `CoreOperations` bounded context, replacing `AggregationStartupWorker` with a generic `OrchestrationStartupWorker`.** This is the deliberate seed of the "central orchestrator" `docs/specs/technical-specs.md` §Feature-Orchestration describes as eventually coordinating Features 1, 2, and 3 sequentially. `RunOrchestrationCommand`'s handler sends `AggregateMusicPreferencesCommand`, waits `TriggerDelaySeconds`, then sends the new `RunAIDiscoveryPipelineCommand` — structured so a future phase can append a third sequential send (Feature 3 / Notification) without rearchitecting. `CoreOperations` uses `docs/constitution/DDD-architecture.md` §2's own listed example context name for exactly this purpose ("handles overarching workflows... high-level orchestration").
2. **Stage output goes through a dedicated `IDiscoveryNotifier` port, not `ILogger` or inline `Console.WriteLine`.** Implemented today as `ConsoleDiscoveryNotifier` (Infrastructure). The user confirmed a future phase will wire Telegram notifications by adding a second implementation of this same interface — so the port's shape must not assume console-only semantics (message content only, no console-specific formatting leaking into Application-layer callers).
3. **Both delays are configurable via `appsettings`, not hardcoded.** `CoreOperationsOptions.TriggerDelaySeconds` (default `30`) and `AIDiscoveryOptions.InterBucketDelaySeconds` (default `10`), bound the same way `AggregatorSettings`/`GeminiOptions` already are. Matches the project's existing convention of externalizing tunable timings, and anticipates real Gemini rate-limit tuning once Stage 2 does real work.
4. **Stage 2 is modeled as a per-bucket sub-pipeline of steps now, not a single monolithic per-bucket handler.** A new `IBucketProcessingStep` abstraction runs an ordered list of steps against each bucket (today: one `PrintBucketStep`). When the two-step Gemini chain (Genre Expansion → Discovery Query) arrives in a future phase, it's added as two new steps without restructuring Stage 2 or the outer pipeline — directly anticipating the complexity growth the source requirements doc calls out.

### Design Notes (Solution-Architect-level implementation calls, not re-litigated with the user)
- **Pipeline pattern, immutable context.** `IAIDiscoveryStage.ExecuteAsync(AIDiscoveryPipelineContext, CancellationToken)` returns a (possibly updated) context; three stages (`StartNotificationStage`, `BucketProcessingStage`, `ReportPublicationStage`) run in strict sequence via `IEnumerable<IAIDiscoveryStage>`, threading the context through. `AIDiscoveryPipelineContext` is an immutable `record` (`SortedBuckets`, `ProcessedBucketCount`), not a Domain value object — it's a transient, Application-layer orchestration artifact with no business invariant of its own, so `DDD-architecture.md` §3's Value Object immutability rule doesn't strictly apply, but immutability was chosen anyway for the same testability/no-hidden-mutation reasons, and because it matches this codebase's existing heavy use of records (`CandidateAlbum`, `DiscoveryPromptRequest`).
- **`IDiscoveryNotifier` is scoped to AIDiscovery pipeline progress signaling — it is explicitly *not* the future Feature 3 Notification bounded context.** `docs/specs/technical-specs.md` §C describes a separate `Notification` context that later consumes `Pending` rows from `DiscoveredAlbums` and dispatches one consolidated Telegram message with YouTube search links — a batch, DB-driven mechanism, distinct from this phase's real-time "the pipeline is running" progress notices. A future Telegram implementation of `IDiscoveryNotifier` (per Decision 2) is a reasonable reuse of the port, but building Feature 3 itself remains fully out of scope here.
- **`DiscoverAlbumsCommand` (Phase 4) was untouched by this phase, then deleted entirely by the Phase 4 rollback recorded above.** `IBucketProcessingStep` remains deliberately named generically so a future phase can add `GenreExpansionStep`/`DiscoveryQueryStep` there — that's now where real Gemini calls will be rebuilt from scratch, rather than by absorbing `DiscoverAlbumsCommand`'s logic, since that code no longer exists.
- **`CoreOperations` is Application-layer-only** — no Domain or Infrastructure code, no repository of its own. It only sequences existing MediatR commands via `ISender`, so it never reaches into another context's domain/repository types directly, satisfying `DDD-architecture.md` §4's cross-context guardrails.
- **`IEnumerable<IAIDiscoveryStage>`/`IEnumerable<IBucketProcessingStep>` resolve in DI-registration order** (documented `Microsoft.Extensions.DependencyInjection` behavior) — the registration order inside `AddApplicationServices` is the single source of truth for pipeline/step ordering and must be preserved carefully as more stages/steps are added in future phases. ## Phase 6: Bucket Aggregator Engine Refinements — Country Normalization & Filtering — ✅ COMPLETE (2026-08-13)

**Source:** `docs/requirements/phase6-requirements.md` (Antigravity-owned input spec — see `.agents/rules/multi-agent-governance.md`), finalized here after clarification.

### Goal
Refine the Phase 3 `BucketAggregatorEngine` with a normalization pre-pass and a filtering post-pass, so buckets are targeted to specific, real countries instead of splintering across country-name synonyms or surviving as continent-level/invalid-country noise. Concretely: (1) before aggregation, `LovedTrackPreferences.Country` values are normalized against `country-synonyms.json` (e.g. `"United States"` → `"USA"`) so synonym variants contribute to the same threshold bucket; (2) after aggregation, two independent rules run over the resulting buckets against `countries-languages.json` as master data — dropping a continent-level bucket (e.g. `"Europe"`) whenever any other bucket resolves to a specific country within that continent, and dropping any bucket whose `Country` isn't a recognized country or continent at all (including today's `"Unknown"` fallback).

### Decisions (confirmed with user 2026-08-13)
1. **Normalization is a new pure Domain type (`CountryNormalizer`), not folded into `LovedTrackRepository`.** Mirrors how `AggregationThresholds` already crosses the Domain/Application boundary as a plain value handed in from Application: `CountryNormalizer.Normalize(tracks, synonyms)` takes an in-memory `IReadOnlyDictionary<string,string>` and returns a new track list, with zero I/O of its own. This keeps `BucketAggregatorEngine`'s "pure, zero-dependency" contract untouched, keeps synonym mapping unit-testable in isolation at the Domain level, and matches `docs/constitution/coding-principles.md` §4's guidance that shared business rules belong in the Domain layer. `LovedTrackRepository.NormalizeCountry` is untouched — it keeps doing only its existing null/empty-to-`"Unknown"` job.
2. **Post-processing filtering is an extensible `IBucketFilterRule` pipeline, not a single hardcoded method.** Mirrors Phase 5's `IAIDiscoveryStage`/`IBucketProcessingStep` pattern: an `IBucketFilterRule` interface with two Domain implementations today (`InvalidCountryDeletionRule`, `ContinentFallbackEliminationRule`), resolved as `IEnumerable<IBucketFilterRule>` and folded over the bucket list in strict DI-registration order inside `AggregateMusicPreferencesCommandHandler`. Unlike Phase 5's stages (which needed `IDiscoveryNotifier` I/O and therefore had to live in Application), these two rules are pure/deterministic with no I/O, so the interface and both implementations live in **Domain**, not Application — a purer fit for `DDD-architecture.md` §1's zero-dependency mandate than the Phase 5 precedent required. Registration order is **`InvalidCountryDeletionRule` before `ContinentFallbackEliminationRule`**: junk/invalid-country buckets are cleared out first, so continent-fallback evidence is only ever evaluated against already-validated country data.
3. **Rule A's "specific country bucket exists within that continent" check counts a bucket of *any* `BucketType`** (`Country`, `CountryLanguage`, or `CountryLanguageGenre`), not only top-level `Country`-type buckets. A country that cascaded all the way to language/genre buckets (and therefore has no `Country`-type bucket of its own) still counts as evidence its continent is represented — reading the source requirement's "any other buckets representing a specific country" literally.
4. **`"Unknown"` buckets (today's fallback for null/empty `CountryOrRegion`) are deleted by Rule B, same as any other unrecognized value.** `"Unknown"` isn't a country or continent in `countries-languages.json`, and the source requirement's own examples of invalid data (`"Global/Various"`, `"Unknown"`, random strings) name it explicitly — no special-casing. This is a deliberate behavior change from Phase 3, where `"Unknown"` buckets were valid output.
5. **All country-name matching (synonym lookup, master-data lookup, continent-name lookup) is case-insensitive.** Track data and JSON master-data keys aren't guaranteed to agree on casing; `CountryMasterData` and `CountryNormalizer` both use `StringComparer.OrdinalIgnoreCase` internally. Not asked of the user — a safe default consistent with how the rest of the codebase treats free-text external input defensively.
6. **`countries-languages.json` is reused from its existing Phase 5 location (`Gemini/Assets/`), not duplicated into a second `MusicAggregator/Assets/` copy.** Only `country-synonyms.json` is newly copied into `src/NewAlbumsDiscovery.Infrastructure/MusicAggregator/Assets/`, per the source spec's explicit instruction for that file. Duplicating `countries-languages.json` a second time would violate DRY for no benefit, since both consumers (this phase and the still-unused Gemini prompts) need identical content.

### Design Notes (Solution-Architect-level implementation calls, not re-litigated with the user)
- **`CountryMasterDataEntry` and `CountryMasterData` are new Domain value types**, not raw dictionaries passed around. `CountryMasterDataEntry(string Continent)` is the minimal shape needed for filtering (no `Language` field — YAGNI, nothing in this phase consumes it); `CountryMasterData` wraps an `IReadOnlyDictionary<string, CountryMasterDataEntry>` plus a precomputed distinct-continents set, exposing `IsKnownCountry(string)`, `IsContinentName(string)`, `TryGetContinent(string, out string?)`. This avoids duplicating continent-set-computation logic across both filter rules and gives future rules (Phase 7+) a single well-tested lookup surface instead of raw dictionary poking.
- **The Australia edge case is handled structurally, not by a special-cased exemption.** `countries-languages.json` maps `"Australia"` to `Continent: "Oceania"` — since `"Australia"` itself is never a member of the distinct-continents set (`{Asia, Europe, Africa, North America, South America, Oceania}`), `ContinentFallbackEliminationRule` never even considers an `"Australia"` bucket a candidate for elimination in the first place. A dedicated regression test locks this behavior in explicitly rather than relying on it being an implicit consequence of the data.
- **`ICountryMasterDataProvider` is a new Application-layer port**, implemented by `EmbeddedCountryMasterDataProvider` in Infrastructure, registered `AddSingleton` (the underlying JSON never changes at runtime, so there's no reason to re-parse per scope/request — unlike the per-request-scoped repositories). - **`AggregateMusicPreferencesCommandHandler` grows three new dependencies**: `ICountryMasterDataProvider`, `CountryNormalizer`, `IEnumerable<IBucketFilterRule>`. Its `Handle` method now: fetches tracks → fetches synonyms → normalizes tracks → builds thresholds (unchanged) → runs `BucketAggregatorEngine.Aggregate` (unchanged) → fetches master data → folds the bucket list through each filter rule in order → persists via `ReplaceAllAsync` (unchanged). ## Phase 7: AI Discovery Prompt Preparation — ✅ COMPLETE (2026-08-13)

**Source:** `docs/requirements/phase7-requirements.md` (Antigravity-owned input spec — see `.agents/rules/multi-agent-governance.md`), finalized here after clarification.

### Goal
Refine Stage 2 of the AIDiscovery pipeline (`BucketProcessingStage`, Phase 5) so that, for every non-instrumental bucket, the exact Markdown prompt(s) needed for a future Gemini call are rendered from the templates in `docs/specs/assets/prompts/` and printed to the console — no actual Gemini API calls this phase. `{{maxAlbums}}` comes from configuration; `{{timeframe}}` is computed at runtime from `TimeProvider` as a rolling 30-day window ending "today". Which template(s) print, and which placeholders get substituted, depends on the bucket's `BucketType` and whether its `Language` is exactly `"Instrumental"`.

### Decisions (confirmed with user 2026-08-13)
1. **Two new `IBucketProcessingStep` implementations — `GenreExpansionPromptStep` and `DiscoveryQueryPromptStep` — not one combined step.** Each independently checks the Instrumental-exclusion rule and no-ops when it doesn't apply, mirroring `PrintBucketStep`'s single-responsibility shape and the interface's own doc comment, which already anticipated "Genre-Expansion and Discovery-Query steps." Both are registered in `IBucketProcessingStep` order after the existing `PrintBucketStep`, so the standard name/track-count line always prints first.
2. **Template loading is Infrastructure; placeholder substitution is a new pure Domain type.** A new Infrastructure port `IPromptTemplateProvider` (implemented by `EmbeddedPromptTemplateProvider`, mirroring `ICountryMasterDataProvider`/`EmbeddedCountryMasterDataProvider`) loads raw `.md` text by file name from embedded resources. A new pure Domain type `PromptRenderer` performs `{{token}}` → value substitution given a template string and a dictionary — zero-dependency, fully unit-testable, consistent with Phase 6's Domain-purity precedent. The `{{timeframe}}` date-range computation is likewise a pure Domain type, `TimeframeFormatter`, taking a `DateTimeOffset` (supplied by the Application layer via `TimeProvider.GetUtcNow()`) rather than reading the clock itself.
3. **Source spec's "Level 3a: Country + Genre (No Specific Language)" is dropped — bucket-to-template selection maps 1:1 onto the three real `BucketType` values instead of the spec's four conceptual levels.** `AggregatedBucket.BucketType` only has `Country`, `CountryLanguage`, and `CountryLanguageGenre`; `BucketAggregatorEngine` (Phase 3) always attaches a `Language` whenever it cascades to the Genre level, so a bucket with a `Genre` but no `Language` cannot occur today. Building code and default-language-fallback logic for an unreachable bucket shape would violate the YAGNI/no-speculative-code guidance in `docs/constitution/coding-principles.md`. Consequently: `country-genres-prompt.md` and any country-default-language lookup are **not** wired up this phase (they remain unconsumed, same as they already were after Phase 5). `CountryLanguageGenre` buckets are treated as the spec's "Level 3b" uniformly — `genre-expansion-prompt.md` substitutes `{{genre}}`/`{{country}}`/`{{language}}` directly from the bucket's own (always-present) `Language`, never a fallback. If a future phase introduces a genre-without-language bucket shape, this mapping can be revisited then.
4. **Rendered prompts reach the console through a new `IDiscoveryNotifier.NotifyPromptRenderedAsync(header, content, cancellationToken)` method**, not raw `Console.WriteLine` in the new steps — keeps all console I/O behind the same testable notifier port `PrintBucketStep` already uses, so the new steps stay infrastructure-agnostic and mockable in Application tests. `ConsoleDiscoveryNotifier` implements it as two `Console.WriteLine` calls (header line, then content).
5. **Prompt headers are fixed by role, not by sequential position.** `GenreExpansionPromptStep` always prints `--- PROMPT 1: GENRE EXPANSION ---` (only fires for `CountryLanguageGenre` buckets); `DiscoveryQueryPromptStep` always prints `--- PROMPT 2: DISCOVERY QUERY ---` (fires for every non-instrumental bucket). For Level 1/2 buckets only "PROMPT 2" appears, with no "PROMPT 1" line — the numbering identifies each prompt's fixed role rather than counting how many prompts printed for a given bucket, while still matching the literal header text in the source spec's example output.
6. **`NewAlbumsDiscovery:AIDiscovery:MaxAlbumsPerQuery` defaults to `20`** (new `AIDiscoveryOptions.MaxAlbumsPerQuery`, added to `appsettings.json`), matching the illustrative "maximum of 20 albums" text already present in the prompt templates themselves. Not asked of the user — a reasonable default for a value the spec only says must be configurable, without prescribing a number.

## Phase 9: Gemini API Integration (Genre Expansion Only) — ✅ COMPLETE (2026-08-14)

### Goal
Wire the `GenreExpansionPromptStep` up to the real Gemini API for non-instrumental Level 3 (`CountryLanguageGenre`) buckets: send Prompt 1 to Gemini instead of printing it, parse the returned genre list, retry transient failures on a configurable backoff, abandon buckets whose calls fail permanently, and feed the resolved genres into `DiscoveryQueryPromptStep`'s `{{genres}}` substitution in place of the current hardcoded `"TBD"`. ### Decisions (confirmed with user 2026-08-14)
1. **API access method:** Raw `HttpClient` against the Gemini REST `generateContent` endpoint. No SDK package (e.g. `Mscc.GenerativeAI`, removed in the Phase 4 rollback) is reintroduced — full control over request/response shape and retry classification, no new dependency.
2. **Missing API key:** Fail-fast at Worker startup. `InfrastructureServiceCollectionExtensions.AddInfrastructureServices` gains a check mirroring the existing `LovedTracksDbPath` pattern — if `NewAlbumsDiscovery__GeminiApiKey` is unset, the Worker throws `InvalidOperationException` and the pipeline never runs. Avoids burning ~220s of retry delay per bucket on a guaranteed-to-fail run.
3. **Retry scope:** Not all failures are retried equally. HTTP `400`/`401`/`403` (bad request / invalid or unauthorized key) are treated as non-transient and abandon the bucket immediately, with zero wait. All other failures — timeouts, network exceptions, `429`, `5xx` — are transient and go through the full configured backoff ladder (`RetryBackoffSeconds`, default `[10, 30, 180]`) before abandonment.
4. **Live verification:** Automated tests only. `IGeminiClient` is fully mocked in Application-layer tests per `docs/constitution/tdd.md` §3's Infrastructure Isolation rule; no real Gemini API call is made as part of this phase's own "done" verification. (The user may run a live check separately afterward.)
5. **Where the retry loop lives:** In `GenreExpansionPromptStep` (Application), not the Infrastructure adapter. `IGeminiClient.GenerateContentAsync` is single-attempt only — it just makes one HTTP call and classifies the outcome. The retry *policy* (how many attempts, how long to wait, when to give up) is a business rule that belongs in Application, testable via `Moq<IGeminiClient>` + a fake `TimeProvider` without any real network or resilience-library dependency — consistent with this codebase's existing no-Polly, hand-rolled-`TimeProvider`-retry precedent (Phase 4 rollback notes, `docs/requirements/FUNCTIONAL_REQUIREMENTS.md` history).
6. **Genre resolution:** A successful response's JSON array of strings is joined with `", "`. An empty array, or JSON that fails to parse despite a successful HTTP call, falls back to the bucket's own original `Genre` value — this is a local fallback, not a Gemini failure, so it never triggers a retry or abandonment.
7. **State handoff / abandonment mechanism:** `IBucketProcessingStep.ProcessAsync` gains a new `BucketProcessingState` parameter — a per-bucket, mutable, Application-only coordination object (not a Domain concept), created fresh by `BucketProcessingStage` immediately before each bucket's step loop. `GenreExpansionPromptStep` sets `state.ResolvedGenres` on success, or calls `state.Abandon()` after a non-retryable or retry-exhausted failure. `BucketProcessingStage` checks `state.IsAbandoned` after every step and breaks the inner loop, skipping any remaining steps (i.e. `DiscoveryQueryPromptStep`) for that bucket. This is a breaking, same-phase signature change to `IBucketProcessingStep` and all three implementations (`PrintBucketStep`, `GenreExpansionPromptStep`, `DiscoveryQueryPromptStep`) — no back-compat overload, consistent with Phase 8's precedent for in-phase breaking changes.
8. **Console output for Prompt 1 stops entirely.** The rendered `genre-expansion-prompt.md` content is sent only to Gemini, never printed — `GenreExpansionPromptStep` drops its `NotifyPromptRenderedAsync` call. Prompt 2 console printing (`DiscoveryQueryPromptStep`) is unchanged from Phase 7/8.
9. **`GeminiOptions` gains two members and one changed default:** `RetryBackoffSeconds` (`int[]`, default `[10, 30, 180]`) and `ApiKey` (`string`, bound separately from the flat `NewAlbumsDiscovery:GeminiApiKey` config key via `PostConfigure`, since — per the existing Phase 2 env-var convention — it lives outside the nested `Gemini:` section). `Model`'s default changes from `"gemini-1.5-flash"` to `"gemini-3.5-flash"` per `phase9-requirements.md` §2.
10. **Pipeline reporting gains an abandonment tally.** `AIDiscoveryPipelineContext` gains `AbandonedBucketCount` (default `0`); `IDiscoveryNotifier.NotifyPipelineCompletedAsync` grows an `abandonedBucketCount` parameter, and a new `NotifyBucketAbandonedAsync(bucketName, trackCount, reason, cancellationToken)` method is added. Both are breaking, same-phase changes to the port and its one implementation (`ConsoleDiscoveryNotifier`).

### Design Notes (Solution-Architect-level implementation calls, not re-litigated with the user)
- **Failure classification lives entirely in the Infrastructure adapter.** `GeminiHttpClient` inspects the HTTP status code (or catches network/timeout exceptions) and returns a `GeminiCallResult` already tagged `IsTransientFailure: true/false`. `GenreExpansionPromptStep` never touches an `HttpStatusCode` — it only branches on the pre-classified boolean, keeping HTTP concerns out of the Application layer per `docs/constitution/tdd.md` §3's Infrastructure Isolation rule.
- **Fallback and abandonment are different failure modes, not the same code path.** A 200-OK response whose body is an empty array or unparsable JSON is *not* a Gemini API failure — `GenreExpansionPromptStep.ResolveGenres` handles it locally by falling back to the bucket's own `Genre`, with no retry and no abandonment (`phase9-requirements.md` §3.2). Only a failed HTTP call (per Decision 3's transient/non-transient split) goes through the retry/abandon path.
- **`ProcessedBucketCount` keeps its current meaning** — every bucket the pipeline visits, including abandoned ones, since `PrintBucketStep` always runs first regardless of what happens afterward. `AbandonedBucketCount` is an independent, additive tally of the subset that hit a Gemini failure; the two numbers are reported side by side (`"Total Buckets Processed: 120 | Total Buckets Abandoned: 2"`), not as parts of two different pools.
- **No Domain changes this phase.** `AggregatedBucket` is untouched; everything new lives in Application (pipeline contract, retry policy, options) and Infrastructure (HTTP adapter, DI wiring).
- **`Microsoft.Extensions.Http` is a new package** (added to `Directory.Packages.props` and the Infrastructure `.csproj`) to get `IServiceCollection.AddHttpClient<TClient, TImplementation>()` for `GeminiHttpClient`'s typed `HttpClient`.

## Phase 10: Gemini API Integration (Discovery Query & Persistence) — ✅ COMPLETE (2026-08-14)

### Goal
Complete the Gemini API integration by executing `DiscoveryQueryPromptStep`'s Prompt 2 against the real Gemini API (it currently only prints), parsing the returned `(Artist, Album)` list, deduplicating against both the current run and all prior runs, persisting the newly-discovered unique albums to a new `DiscoveredAlbums` table with `Status = Pending`, and expanding `ReportPublicationStage` into a full statistical report of the run (10 metrics per `docs/requirements/phase10-requirements.md` §4).

### Decisions (confirmed with user 2026-08-14)
1. **Abandonment console format**: Discovery Query reuses the exact same `ConsoleDiscoveryNotifier.NotifyBucketAbandonedAsync` call/format already used by Genre Expansion (`"AIDiscovery: bucket '{bucketName}' ({trackCount} track(s)) ABANDONED - {reason}"`) — not the slightly different literal string in `phase10-requirements.md` §2 (em dash, no track count). The doc's wording was descriptive, not a literal spec.
2. **"Processed Successfully" count** (`phase10-requirements.md` §3): `{Count}` is the number of albums newly persisted for that bucket, *after* dedup — not the raw count Gemini returned. This also becomes the number tracked per-bucket for the Stage 3 report metrics.
3. **`DiscoveredAlbums` → bucket reference**: a real `ReferenceBucketId` FK (`Guid`) to `AggregatedBuckets.Id`, per the deleted Phase 4 design precedent — not a bucket-name string as `phase10-requirements.md` §3's looser wording suggested.
4. **FK delete behavior — `ON DELETE CASCADE`, deliberately accepted**: `AggregatedBucketRepository.ReplaceAllAsync` does an unconditional `DELETE FROM AggregatedBuckets` + reinsert on *every* pipeline run (not just when something changed) — see `docs/requirements/phase3-requirements.md` §6. With a cascading FK, this means **every scheduled run wipes every `DiscoveredAlbums` row from all prior runs** before that run's own AIDiscovery stage even starts. The user explicitly confirmed this tradeoff after it was flagged: in practice, "dedup against a past run" and "persist `Pending` albums for later review" (Feature 3) both only span a single run's lifetime today — a `DiscoveredAlbums` row never survives past the next scheduled aggregation. The dedup-against-history query is still implemented per the letter of the requirement (and matters for same-day/manual re-runs before the next aggregation), but should not be relied on as durable cross-run storage as currently wired. Revisiting bucket persistence to stop wiping (e.g. upsert-by-name) is explicitly out of scope for this phase.
5. **`DiscoveredAlbumStatus` enum — `Pending` only.** No `SendForReview` or other Feature 3 values added speculatively; those land when Feature 3 is actually implemented.
6. **Malformed/unparsable Discovery Query JSON (200 OK, bad body)**: treated as 0 albums found for that bucket — not abandoned, no retry. Mirrors Phase 9's "parse issues aren't API failures" precedent for Genre Expansion's fallback. Counts as an "Empty Bucket" in the Stage 3 report, not a "Bucket Skipped." Acknowledged risk: a genuinely broken response is indistinguishable from a bucket that legitimately found nothing.
7. **Highest/Lowest Yield Bucket ties**: all tied bucket names are listed (e.g. `"BucketA, BucketC (12 albums)"`), not just the first one encountered.
8. **`DiscoveredAlbum` property names — `Artist` / `AlbumName`** (Solution-Architect call): the two source docs disagreed (`technical-specs.md` says `AlbumName`; the deleted Phase 4 entity used `Album`). Followed `technical-specs.md` as the more current architecture spec.
9. **Retry policy code is shared, not duplicated** (Solution-Architect call): `GenreExpansionPromptStep`'s hand-rolled retry loop (Phase 9) is extracted into a new `GeminiRetryExecutor` Application-layer helper, reused by both `GenreExpansionPromptStep` (refactored, no behavior change — Phase 9's tests must still pass unmodified in intent) and the new Discovery Query retry call. Required by `docs/constitution/coding-principles.md` DRY guidance now that a second, near-identical retry loop would otherwise exist.
10. **Discovery Query parsing and persistence are separate pipeline steps** (Solution-Architect call): `DiscoveryQueryPromptStep` renders the prompt, calls Gemini (via the shared retry executor), and parses the response into candidate `(Artist, Album)` pairs onto `BucketProcessingState`. A new `AlbumPersistenceStep` (runs immediately after it in the Stage 2 step list) deduplicates and persists them, and fires the "Processed Successfully" notification. Keeps each step single-responsibility, consistent with the existing `PrintBucketStep` / `GenreExpansionPromptStep` / `DiscoveryQueryPromptStep` split.

### Design Notes
- **Dedup mechanism**: `BucketProcessingStage` loads the full set of existing `AlbumKey`s (normalized, case-insensitive, trimmed `(Artist, Album)` pairs) from `IDiscoveredAlbumRepository` **once**, at the start of `ExecuteAsync`, into a single mutable `ISet<AlbumKey>`. That same set is threaded through every step's `ProcessAsync` call for every bucket in the run (a new parameter, not a new per-bucket or per-run wrapper object) and is mutated in place by `AlbumDeduplicator.SelectNew` inside `AlbumPersistenceStep` as each bucket's new albums are accepted — so a duplicate surfacing in bucket #50 that was already accepted from bucket #3 earlier in the *same* run is caught without a DB round-trip, and duplicates against prior runs are caught by the initial load. This restores the Phase 4 `AlbumDeduplicator` design (mutates the caller's set, first-occurrence-wins within a batch) rather than reinventing it.
- **`IBucketProcessingStep.ProcessAsync` signature changes again** (third time, after Phase 7 and Phase 9): gains `ISet<AlbumKey> existingAlbumKeys`. `PrintBucketStep`, `GenreExpansionPromptStep`, and `DiscoveryQueryPromptStep` all ignore it (unused parameter, consistent with the existing precedent of `PrintBucketStep` ignoring `BucketProcessingState`); only `AlbumPersistenceStep` uses it. A clean breaking change within the phase, not a back-compat shim, consistent with this project's established practice.
- **`BucketProcessingState` gains two fields**: `DiscoveredCandidates` (`IReadOnlyList<(string Artist, string Album)>`, default empty, set by `DiscoveryQueryPromptStep`) and `PersistedAlbumCount` (`int`, set by `AlbumPersistenceStep`, read by `BucketProcessingStage` when building that bucket's `BucketOutcome`). Still created fresh per bucket — the cross-bucket concern (dedup) lives in the separately-threaded `existingAlbumKeys` set instead, not on this per-bucket object, preserving its documented per-bucket-only invariant from Phase 9.
- **New `BucketOutcome` record** (`(string BucketName, BucketType BucketType, bool WasAbandoned, int AlbumsDiscovered)`), appended by `BucketProcessingStage` for every bucket it visits (abandoned or not), collected into `AIDiscoveryPipelineContext.BucketOutcomes` (new property, replacing nothing — `ProcessedBucketCount`/`AbandonedBucketCount` are unchanged and still computed the same way). `ReportPublicationStage` computes all 10 report metrics purely from this list via a new pure/static `DiscoveryRunReportCalculator`, independently unit-testable without mocking the notifier.
- **Level 1/2/3 in the report map directly onto `BucketType`** (`Country` / `CountryLanguage` / `CountryLanguageGenre`) — confirmed no separate "level" concept exists or is needed; this was settled in Phase 7 (`FUNCTIONAL_REQUIREMENTS.md` → Phase 7 → Decision 3) and Phase 10 just reads it.
- **Average/Highest/Lowest exclusion rule applied consistently**: per `phase10-requirements.md` §4.5 ("Exclude skipped buckets and buckets with 0 albums") and §4.10 ("ignoring empty/skipped buckets" for lowest yield), the same eligibility filter (`!WasAbandoned && AlbumsDiscovered > 0`) is applied to the overall average, all three per-level averages, *and* both highest and lowest yield (the doc only states the exclusion explicitly for the overall average and lowest yield; applying it to highest yield too, for consistency, is a Solution-Architect judgment call — a bucket that "won" only because everything else was empty or skipped is not a meaningful highest-yield signal either). If no bucket is eligible, all four average metrics report `null`/`"N/A"` and highest/lowest yield report `"N/A"` rather than dividing by zero or picking an empty/abandoned bucket.
- **Console report format** (`ConsoleDiscoveryNotifier.NotifyDiscoveryReportAsync`, printed by `ReportPublicationStage` before the existing `NotifyPipelineCompletedAsync` line, which is unchanged):
  ```
  === AIDiscovery Run Report ===
  Total Buckets: {TotalBuckets}
  Buckets Skipped: {BucketsSkipped}
  Empty Buckets: {EmptyBuckets}
  Total Albums Discovered: {TotalAlbumsDiscovered}
  Average Albums per Bucket: {F2 or "N/A"}
  Average Albums per Level 1 Bucket (Country): {F2 or "N/A"}
  Average Albums per Level 2 Bucket (Country+Language): {F2 or "N/A"}
  Average Albums per Level 3 Bucket (Country+Language+Genre): {F2 or "N/A"}
  Highest Yield Bucket: {name(s) comma-joined} ({count} albums)  [or "N/A"]
  Lowest Yield Bucket: {name(s) comma-joined} ({count} albums)  [or "N/A"]
  ```
- **`NotifyPromptRenderedAsync` is removed from `IDiscoveryNotifier`/`ConsoleDiscoveryNotifier`.** `DiscoveryQueryPromptStep` was its only caller (`phase10-requirements.md` §2: "MUST STOP printing the Discovery Query prompt to the console"); Genre Expansion already stopped calling it in Phase 9. Removing rather than leaving unused, per the project's no-dead-code guidance.
- **`DiscoveredAlbumRepository.AddRangeAsync` is additive** (no delete/replace), unlike `AggregatedBucketRepository.ReplaceAllAsync` — persistence happens once per bucket, immediately after that bucket's dedup, inside `AlbumPersistenceStep`, so a mid-run interruption still keeps every already-processed bucket's discoveries.
